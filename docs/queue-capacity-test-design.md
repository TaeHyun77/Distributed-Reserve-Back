# 대기열 → 예약 Capacity 측정 설계

작성일: 2026-06-13 · 목적: 대기열(waiting-room)이 예약 시스템으로 흘려보낼 **입장 인원/속도**를 신뢰성 있게 산정

> 핵심 원칙:
> **입장량 = (운영급 HW에서 / 현실 좌석 경합 하에서 / 풀 경로로) 측정한 지속가능 처리량 × 안전계수.**
> 그리고 한 번 잰 정적 숫자가 아니라, 실시간 지표로 자동 조절하는 **적응형 대기열**이 최종 신뢰성을 만든다.

> ★ 프레이밍 교정 (버스트 vs 지속 — 같은 질문이 아니다):
> **참가열 capacity(N) 자체는 "지속(soak)"으로 정한다.** N 은 상주 인구이고, think-time 이 부하를 분산시키므로 슬롯 점유(N)와 DB 동시성은 디커플링된다 → N 의 상한은 "지속 상태에서 풀/DB 가 버티는가"가 결정한다.
> **버스트는 capacity 가 아니라 "승격 속도(대기열→참가열 admission rate·배치 크기)"를 정하는 별도 손잡이다.** 배치 승격이 think-time 분산을 깨 순간 λ 를 치솟게 하므로, 버스트가 아프면 N 을 줄이는 게 아니라 *한 틱에 승격하는 인원(B)* 을 제한한다.

---

## 0. 산출물
1. 입장 파라미터: **입장 rate(λ, 명/초)** 또는 **동시 예약 인원(N명)** + 안전계수.
2. 그 숫자의 근거(측정 조건·SLO·마진).
3. 적응형 대기열의 제어 지표·임계값.

---

## 1. 기존 "병목 탐색 테스트"와 무엇이 다른가 — 3대 보정

| 항목 | 기존(병목 탐색) | **capacity 측정용** |
|---|---|---|
| 환경 | Mac M4 Docker, 생성기 동거 | **운영/스테이징급 HW + 생성기 별도 머신** |
| 부하 모델 | 유저·좌석 유니크(**경합 0**) | **현실 좌석 경합**(인기 좌석 몰림·충돌·매진) |
| 경로 | NoOp 메일·내부 결제 | **풀 경로**(실 메일/결제 지연, 운영 데이터, 혼합 트래픽) |
| 목표 | 상대 비교·병목 식별 | **절대 capacity + 안전 마진** |

> 기존 숫자(850/500)는 *경합 없는·비운영 HW의 낙관적 상한*이라 입장 인원으로 쓰면 위험. 이 설계는 그 셋을 모두 보정한다.

---

## 2. 무엇을 측정하나 — 대기열이 실제로 제어하는 단위

- **예약 세션**의 정의를 먼저 고정: 입장 → 좌석 선택 → 결제 완료까지(사용자 think-time 포함).
- 두 가지 제어 framing (대기열 구현에 맞춰 택1, 권장은 둘 다 측정 후 변환):
  - **rate 제어**: 초당 λ명 입장 (token/leaky bucket).
  - **concurrency 제어**: 동시에 N명만 예약방 입장.
  - 변환은 리틀의 법칙: **N = λ × W** (W = 평균 세션 시간). think-time이 길면 같은 rate라도 동시 인원이 커짐 → DB 커넥션·락 점유가 늘어남에 유의.

---

## 3. 부하 모델 — 현실 경합 (이 설계의 심장)

대기열 use case의 1순위 변수는 **경합**이다. 두 시나리오로 측정:

- **시나리오 A — worst-case (입장 인원 산정 기준):**
  - 인기 단일 스케줄, 좌석 N석에 사용자가 몰림.
  - **좌석 선택 분포에 핫스팟**(다수가 "좋은 좌석" 먼저) → seat row 락 경합 극대화.
  - 충돌 시 재시도(다른 좌석), **매진 처리**(재고 소진 후 거동) 포함.
- **시나리오 B — 평균(여러 스케줄 분산):** 일상 capacity 참고용.

핵심 파라미터: 좌석 수, 선택 집중도(핫스팟 비율), 충돌 재시도율, think-time, 동시 활성 이벤트 수.
→ **A로 안전한 하한(입장 인원), B로 평균 처리량**을 함께 제시.

---

## 4. 운영 충실도 (풀 경로)
- **이메일**: 실 SMTP 또는 *대표 지연을 가진 스텁*(운영의 발송 지연/스로틀 반영).
- **결제**: 실 PG 연동 지연 또는 지연·실패율 모델.
- **데이터셋**: 운영 규모(캐시 미스 발생하도록).
- **혼합 트래픽**: 예약 + 취소 + 조회를 운영 비율로 동시 주입.
- 인증 포함 시 **운영 BCrypt cost** 적용.

---

## 5. SLO — 측정 전에 정의 (입장한 사용자에게 주는 보장)
- 예약 end-to-end **p95 < X초**, **error < Y%**, 그리고 **정합성: 오버셀 0**(예약 좌석 ≤ 재고).
- 한계 = 이 SLO를 **지속적으로** 유지하는 최대 입장 rate.

---

## 6. 테스트 종류 — knee 하나로 끝나지 않는다
1. **경합 하 steady-state 스윕** → SLO 깨지는 knee 탐색.
2. **지속 soak (30–60분)** → 메모리 누수·커넥션 고갈·락 누적·리플리카 지연 등 *시간이 지나야 터지는* 문제.
3. **버스트 테스트** → 대기열 방출은 버스트(배치 입장). 한 번에 N명 들어와도 흡수되나.
4. **과부하 거동** → 한계 초과 시 graceful degradation인가 cliff인가(클라이언트 경험·복구).
5. **정합성 검증** → 부하 중 *오버셀 0* 단언(같은 좌석 이중 예약 없음).

---

## 7. 측정 → 입장 파라미터 산정
- **입장 rate = sustainable_rate(시나리오 A) × 안전계수(0.5–0.7)**
- 동시 인원 제어면: **N = sustainable_rate × W × 안전계수** (또는 직접 concurrency 스윕).
- **안전계수 근거**: 측정 분산 + 트래픽 스파이크 헤드룸 + (knee ≠ 안전 운영점) 격차 + 성장 여유.
  - knee의 100%로 운영하면 작은 변동에도 SLO 붕괴 → 절대 금지.

---

## 8. ★ 정적 숫자 → 적응형 대기열 (가장 중요한 운영 권고)
한 번 잰 capacity는 **"초기값 + 상한 가드레일"**일 뿐이다. 트래픽 믹스·새 이벤트 유형·인프라 변화에 정적 숫자는 취약하다.

- 대기열을 **closed-loop**로: 예약 시스템의 실시간 지표를 모니터해 입장 속도를 자동 조절.
  - 관측: 예약 p95 latency, error rate, **DB 커넥션 pending**, app/DB CPU.
  - 제어: 지표가 임계 이하면 입장 가속, 초과하면 감속(예: **AIMD** — 정상 시 선형 증가, SLO 위반 시 급감).
- 측정으로 얻은 capacity는 이 루프의 **상한선**과 **초기 설정값**으로 사용.
- → "측정한 숫자를 박아두기"보다 **"측정으로 안전 범위를 정하고, 그 안에서 실시간 적응"**이 진짜 신뢰성.

---

## 9. 신뢰성 규율 (기존 보고서와 동일하게 적용)
- **생성기 별도 머신 + dropped=0 증명**(절대값이 의미를 가지려면 필수).
- 운영급 HW, **3회 반복** 중앙값+범위, 백투백.
- 부하 중 **정합성 단언**(오버셀 검증).

---

## 10. 폴백 — 운영급 HW/생성기 분리가 불가할 때 (현재 Mac 제약)
절대 capacity는 못 낸다. 대신:
- 경합 모델 + 풀 경로로 **보수적 하한 + 병목 형태**만 확보.
- **적응형 대기열에 더 의존**(정적 숫자를 못 믿으므로).
- **운영 카나리**: 소규모 실트래픽을 점진 증가시키며 실제 한계를 *현장에서* 탐색(가장 신뢰도 높은 보정).

---

## 11. 구현된 하니스 (방법 A)

이 설계의 측정 절차를 다음 스크립트로 구현했다. ( SLO = 예약 p95<1s & err<1% & 오버셀0, 기존 컨벤션 그대로 )

| 단계 | 도구 | 무엇을 | 산출 |
|---|---|---|---|
| 지속 측정 | `loadtest/scripts/run-soak.sh` | 단일 RATE 를 장시간(기본 30m) 유지 → 전구간 SLO + 오버셀 + **자원 드리프트**(앞1/3 vs 뒤1/3 의 hikari_pending·app_cpu) 판정 | 지속 가능 처리량 **λ_safe** |
| 버스트 게이트 | `loadtest/scripts/run-burst.sh` + `loadtest/k6/reserve-burst.js` | 베이스라인 + "한 틱 배치 승격"(B명 순간투입) 스윕 → 스파이크 p95 + **회복 시간**(pending 복귀) + 오버셀 판정 | 흡수 가능한 **최대 배치 B (승격 배치 상한)** |
| 산출 | `loadtest/scripts/compute-capacity.sh` | `N = λ_safe × W × 안전계수(기본0.6)` + W 민감도 표 | 참가열 **capacity N** + 배치 상한 |

> **범위 의도적 제외 — 읽기 혼합(풀 경로 일부):** 좌석맵 조회(`GET /reserve/seat/get/list/{id}`)가 **무페이징 전체 목록**이라(시드 10만 좌석 = 10만 행 JSON), 운영에선 캐시/리플리카로 처리될 읽기를 비현실적으로 무겁게 잡아 λ 를 왜곡한다. 실제 병목인 **쓰기 경로**에 집중. 읽기 혼합은 페이징/캐시 모델이 생기면 추가.
> **하드웨어 한계:** Mac+생성기 동거라 λ_safe 절대값은 보수적 하한 + 병목 형태로만 신뢰. 최종 신뢰성은 §8 적응형 승격(상한=측정 N, 실시간 AIMD, 매진 임박 시 승격 0)이 만든다.

## 부록 — 기존 하니스에서 바꿀 것
- `reserve-load.js`: 유니크 좌석 → **경합 좌석 분포**(핫스팟), think-time, 충돌 재시도, 매진 처리, **end-to-end 세션** 측정.
- 신규: 소크/버스트 시나리오 스크립트, **오버셀 검증 쿼리**(부하 후 `SELECT COUNT reserved ≤ 재고`).
- 메일/결제: NoOp → **대표 지연 스텁**.
- 모니터: 적응형 대기열용 지표(예약 p95·pending) 실시간 노출.
