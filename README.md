
### 프로젝트 설명
---
예약, 결제, 리워드 지급 등 동시성 이슈가 발생할 수 있는 도메인을 직접 구현하며, 상황에 적합한 동시성 전략을 적용하는 것을 목표로 진행한 프로젝트입니다.

- 예약 생성 시 조건부 UPDATE( 비어 있는 좌석만 원자적으로 선점 )로 동일 좌석에 대한 중복 예약을 방지하고, 멱등성 키( DB unique 제약 기반 선점 )를 적용하여 동일 요청이 반복되더라도
  예약이 한 건만 생성되고 동일한 응답이 반환되도록 하였습니다.

- 예약, 예약 취소, 리워드 지급 과정에서 회원 자원( 크레딧, 리워드 )에 DB 비관적 락을 적용하여 정합성을 보장하고, 예약 취소와 리워드 지급은 상태 체크( 예약 상태, 지급 일자)를 통해 멱등성을 확보하였습니다.<br><br>

### 동시성 이슈
---
분산 서버 환경에서는 여러 인스턴스가 동시에 동일한 자원에 접근하거나 변경하면서 동시성 문제가 발생할 수 있습니다.

비즈니스 로직 내부에 예외 처리를 해두었더라도, 각 서버가 독립적으로 트랜잭션을 수행하면서 모든 요청이 정상 처리되는 것처럼 보이는 현상이 발생할 수 있고, 그 결과 좌석의 중복 예약이나 리워드의 중복 지급 등 데이터 정합성 문제로 이어질 수 있습니다.

이번 프로젝트에서는 자원의 경합 특성과 보호 범위에 따라 조건부 UPDATE(좌석 선점), DB 비관적 락( 회원 크레딧, 리워드 ), 멱등성( unique 제약 + 상태 체크 )을 선택적으로 적용하여 동시성 문제를 해결했습니다. 동시성 제어를 공유 DB 계층에서 보장하므로, 별도의 분산 락 인프라 없이도 다중 인스턴스 환경에서 정합성이 유지됩니다.<br><br>

### 예약 로직에 조건부 UPDATE 방식을 사용한 이유 
---
좌석 예약은 다수 요청이 몰리는 고경합 환경이면서 한 요청이 여러 좌석을 원자적으로 선점해야 하므로, 락 보유 시간이 짧고 단일 UPDATE로 데드락 위험을 구조적으로 낮추면서 이중 예약 방지( 정합성 )를 DB가 직접 보장하는 조건부 UPDATE 방식을 채택했습니다.<br><br>

### 기능 구현
---
1. 조건부 UPDATE로 좌석을 원자적으로 선점하여 좌석 중복 예약 방지

2. 멱등성 키( DB unique INSERT 선점 + 응답 캐싱 )로 중복 요청 시에도 예약 한 건만 생성 및 동일 응답 반환

3. DB 비관적 락으로 예약, 취소, 리워드 지급 시 사용자의 크레딧·리워드 정합성 보장
  
4. 예약 ~ 결제 흐름 전반의 결제 처리 로직 구현

5. 예약/취소 확인 이메일을 트랜잭션 커밋 후 비동기로 발송하여 사용자 메일 알림 처리 (SMTP)

6. 통합·동시성 테스트로 좌석 중복 방지·멱등성·크레딧 직렬화·이중 취소 방지 검증<br><br>

### 트러블 슈팅 및 개선 사항
---
1. 좌석 동시성 제어를 Redis 분산 락( Redisson )에서 조건부 UPDATE + 멱등성 기반으로 전환했습니다. 좌석 중복 예약은 공유 DB의 원자적 조건부 UPDATE와 unique 제약만으로 보장되므로, 외부 락 인프라 의존성을 제거하고 구조를 단순화했습니다.

2. 멱등성 처리에서 PENDING 선점으로 동시 진입을 상호배제하고, task 실행과 상태 확정을 하나의 트랜잭션으로 원자화하여 부분 성공·중복 실행을 방지했습니다.

3. 예약/취소 확인 이메일을 트랜잭션 커밋 후 비동기 발송으로 분리하여, 메일 발송 실패가 예약 트랜잭션에 영향을 주지 않도록 했습니다.

4. 예약 취소 시 회원 비관적 락을 좌석 변경 이전에 획득하도록 순서를 정리하여 예약 흐름과 락 획득 순서를 일치시키고 데드락 가능성을 낮췄습니다.<br><br>

### 테스트
---
[ 기본적인 로직 테스트 ]

좌석 이중 점유 방지, 사용자의 크레딧 및 리워드 정합성, 이중 환불 방지, 멱등성 등등 로직의 기본적인 테스트를 진행하였습니다<br><br>

[ 예약 로직의 부하 테스트 ]

티켓팅 시스템 특성을 고려해 페이지 체류로 인한 지속 부하와 동시 예약 클릭으로 인한 버스트 부하를 분리해 k6로 검증했고, 300~400 RPS까지는 안정적이었으나 450 RPS부터 에러율 50% 이상으로 급격히 무너져 안정 처리량을 400 RPS로 판단했습니다. 

분석 결과 DB는 여유로운 반면( CPU 155/300, 락 경합 0 ) HikariCP 풀( 30 )이 부족해 순간 피크 시 pending이 156까지 쌓이는 것이 지연의 주원인이었고, 풀을 80으로 늘리자 p99가 567ms→121ms로 개선되는 방향성을 확인했습니다. 

이를 바탕으로 입장열의 maxCapacity를 400명으로 설정했으며, 운영 중에는 이를 고정값이 아닌 참고값으로 보고 실시간 지표에 따라 조절할 계획입니다.
