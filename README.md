
### 프로젝트 설명
---
예약, 리워드 지급 등 동시성 이슈가 발생할 수 있는 도메인을 직접 구현하며, 상황에 적합한 동시성 제어 전략을 적용하는 것을 목표로 진행한 프로젝트입니다.

- 예약 생성 로직에 Redisson 기반 분산 락을 적용하여 동일 좌석에 대한 중복 예약을 방지하고, 멱등성 키를 적용하여 네트워크 타임아웃 등으로 동일 요청이 반복되더라도 예약이 한 건만 생성되고 동일한 응답이 반환되도록 하였습니다.

- 예약 취소, 리워드 지급 로직에 DB 비관적 락을 적용하여 크레딧과 리워드의 정합성을 보장하고, 상태 체크를 통해 별도의 멱등성 키 없이 자연 멱등성을 확보하였습니다.<br><br>

### 동시성 이슈
---
분산 서버 환경에서는 여러 인스턴스가 동시에 동일한 자원에 접근하거나 변경하면서 동시성 문제가 발생할 수 있습니다. 

비즈니스 로직 내부에 예외 처리를 해두었더라도, 각 서버가 독립적으로 트랜잭션을 수행하면서 모든 요청이 정상 처리되는 것처럼 보이는 현상이 발생할 수 있고, 그 결과 좌석의 중복 예약이나 리워드의 중복 지급 등 데이터 정합성 문제로 이어질 수 있습니다.

이번 프로젝트에서는 리소스의 경합 특성에 따라 Redis 분산 락과 DB 비관적 락을 적절히 분리 적용하여 동시성 문제를 해결했습니다.<br><br>

### 해결 방안
---
좌석 예약처럼 다수의 사용자가 동일 자원에 동시 접근하여 경합 빈도가 높은 경우, Redis 분산 락을 적용하여 DB 도달 전에 중복 요청을 차단했습니다. 

Redis는 분산 서버 환경에서도 락을 효율적으로 관리할 수 있으며, 애플리케이션 레이어에서 동시성 제어를 수행함으로써 빠른 실패를 유도하여 DB 리소스 낭비를 최소화할 수 있습니다.

반면, 사용자 크레딧이나 리워드처럼 동일 사용자의 동시 요청에서만 경합이 발생하고 트랜잭션 내부에서 완결되는 경우에는 DB 비관적 락을 적용했습니다. 여기에 Redis 락을 추가하면 레이어만 늘어나고 실질적인 이점이 없기 때문입니다.<br><br>

[ 스핀락에서 Redisson으로의 전환 ]
기존에는 SET key value NX EX 명령어 기반의 스핀락 방식으로 분산 락을 구현했습니다. 그러나 이 방식은 개발자가 직접 재시도 및 타임아웃 로직을 구현해야 하고, 요청이 몰릴수록 락 획득을 위한 지속적인 폴링으로 Redis 부하가 커지는 문제가 있었습니다.

Redisson 방식으로 전환한 이유는 아래와 같습니다.
1. Redisson은 Lock 인터페이스를 지원하여 waitTime, leaseTime 등을 간편하게 설정할 수 있고, Pub/Sub 기반으로 락 해제 이벤트를 구독하여 불필요한 폴링 없이 효율적으로 락을 관리합니다.

2. leaseTime을 지정하지 않으면 Watchdog이 활성화되어 락을 보유한 스레드가 살아있는 동안 TTL을 자동 갱신하므로, 트랜잭션 처리 시간이 가변적인 상황에서도 락이 조기 만료되는 위험이 없습니다.

3. 여러 좌석에 동시에 락을 걸어야 하는 상황에서 Redisson의 MultiLock을 활용하여 여러 락을 하나의 논리적 락으로 묶어 all-or-nothing으로 처리할 수 있습니다. 추가로 락 키를 정렬하여 획득 순서를 일관되게 함으로써 데드락 발생 가능성을 방지했습니다.
